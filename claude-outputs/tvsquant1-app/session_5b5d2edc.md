**File:** `tvsquant1-app/app/routers/strategies.py:8`

The Dev Notes in the story (lines 130-131) specify using `StrategyError` from `engine.exceptions`:

```python
# Story Dev Notes specifies:
from engine.exceptions import StrategyError

# ACTUAL CODE:
from strategies.exceptions import StrategyRegistrationError
```

While both work (StrategyRegistrationError extends StrategyError), the architecture pattern states API endpoints should catch the base exception type (`StrategyError`) for consistency with other endpoints like backtests.py which uses:
```python
from engine.exceptions import BacktestConfigError, BacktestError, DataNotFoundError
```

This is inconsistent - `strategies.py` should import from `engine.exceptions` not `strategies.exceptions`.

**File:** `tvsquant1-app/app/routers/strategies.py:84-87`

The `get_strategy()` endpoint makes **two calls** to the registry:

strategy_cls = registry.get_strategy(strategy_id)  # 1st call

### MEDIUM-3: id Field Uses Class Name Instead of Registry Key
**File:** `tvsquant1-app/app/routers/strategies.py:54-55, 93-94`

The `id` field in responses uses `strategy_cls.__name__` instead of the registry key:

```python
# list_strategies():
StrategyListItem(
    id=s.name,        # Uses s.name (class name)
    name=s.name,      # Same value duplicated
    ...
)

# get_strategy():
StrategyDetail(
    id=strategy_cls.__name__,  # Uses class name
    name=strategy_cls.__name__, # Same value duplicated
    ...
)
```

This works for now because strategies are registered with their class names, but `id` and `name` should be semantically different:
- `id`: The registry lookup key (could be different from class name)
- `name`: Display name for UI

This could cause issues if someone uses `@register_signal(name="custom_name")`.
