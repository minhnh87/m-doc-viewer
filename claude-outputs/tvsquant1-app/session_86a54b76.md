## 🔴 CRITICAL/HIGH ISSUES

### HIGH-1: Signal.calculate() return type mismatch with handle_data usage
**File:** `tvsquant1-app/strategies/base.py:186-192`

The `Signal.calculate()` method is documented to return `pd.Series` (line 54-67 docstring), but `handle_data` treats the result as a dict:
```python
# handle_data expects dict-like access:
sig_value = signals.get(sym, 0)  # line 192
```

However, `pd.Series.get()` works differently than dict - it returns NaN (not the default) when key doesn't exist in some pandas versions. The test's `MockSignal.calculate()` returns a Series with explicit keys that works around this, but a real Signal implementation following the docstring would fail.

**Impact:** Runtime bug when using real Signal implementations in production.

---

### HIGH-2: _build_ohlcv_dataframe does NOT return proper OHLCV structure
**File:** `tvsquant1-app/strategies/base.py:204-238`

The method builds `ohlcv_data` dict with separate DataFrames for each field, then creates `pd.DataFrame(ohlcv_data)` which produces nested structure, NOT the documented OHLCV format expected by Signal.calculate().

Looking at the code:
```python
ohlcv_data = {}
for field in ['open', 'high', 'low', 'close', 'volume']:
    history = data.history(...)  # Returns DataFrame or Series per field
    ohlcv_data[field] = history  # Storing whole DataFrame/Series

df = pd.DataFrame(ohlcv_data)  # Creates DataFrame of DataFrames!
```

The `Signal._validate_ohlcv_data()` method expects columns `['open', 'high', 'low', 'close', 'volume']` but this won't work with nested DataFrames.

**Impact:** The adapter would fail with any Signal that uses `_validate_ohlcv_data()`.
