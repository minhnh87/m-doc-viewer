**Issue 1: MEDIUM - `_normalize_trades` mutates input DataFrame**

`trades.py:126-134`:

The method modifies the input DataFrame before copying it. This is a **side effect** that violates pure function principles.

**Issue 2: MEDIUM - No validation for invalid `method` parameter**

`trades.py:363-366`:
```python

    method: str = 'fifo'

```
No validation that `method` is either 'fifo' or 'lifo'. Passing `method='invalid'` will silently use LIFO logic (the else branch).

**Issue 3: LOW - `get_summary()` returns inconsistent `total_trades` counts**

`trades.py:218-234`:
When P&L is all NaN, the `total_trades` returns `len(self._trades)` (line 319) but when P&L has values, it returns `len(pnl)` (line 239). This could cause confusion - does `total_trades` mean "number of trade records" or "number of trades with P&L calculated"?

**Issue 4: MEDIUM - `by_symbol` fails on None symbols**

`trades.py:274`:
```python
mask = self._trades['symbol'].str.upper() == symbol.upper()
```
If `symbol` column contains `None`/`NaN` values, `.str.upper()` will return `NaN`, not raise. However, if a user passes `None` as the `symbol` argument, it will raise `AttributeError: 'NoneType' object has no attribute 'upper'`.

The story's Dev Notes (line 258-273) show handling a nested `row.get('txns', [row])` format, but the actual implementation (trades.py:154-177) doesn't iterate through `txns`. This means the implementation may not handle all zipline transaction formats.

No check if `openpyxl` is installed. This will fail with a cryptic error if the dependency is missing.
